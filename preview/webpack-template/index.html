What it is and what it solves

A build skeleton for projects that need modular JS, not just markup.

The starter solves the same problem as the gulp one — take the repetitive setup out of every new project — by a different route. In gulp the pipeline is written as a sequence of file streams; in webpack a single entry point drags in a dependency graph, and everything else is rules about what to do with each kind of node in it. From that follows the one difference that matters in practice: styles.scss ends up in the build not because someone named its path, but because script.js has an import for it.

What is configured above the minimum: aliases (@scss, @img, @js) instead of ../../ chains; splitChunks: 'all', which pulls dependencies into their own chunk; content hashes in file names for caching; ESLint wired into the build and failing it on an error in production; and a large block of SEO/Open Graph/Twitter meta that HtmlWebpackPlugin injects into the markup.

Key excerpts

Four places that decide how the build behaves.

const isDev  = process.env.NODE_ENV !== "production",
      isProd = !isDev

const filename = ext => isDev ? `[name].${ext}` : `[name].[contenthash].${ext}`

The only mode switch in the whole file. The hash goes into the name in prod only: in dev it would get in the way, producing a new file on every rebuild. The flip side is in the defects list — isDev depends on an environment variable rather than on mode, so the mode is set by the npm script through cross-env, and running webpack directly gives you something other than what you expect.

{
    test: /\.s[ca]ss$/,
    use: [
        isDev ? "style-loader" : MiniCssExtractPlugin.loader,
        { loader: "css-loader", options: { sourceMap: isDev } },
        { loader: "sass-loader", options: {
            implementation: require.resolve("sass"),
            api: "modern",
            sassOptions: { outputStyle: "compressed" }
        }}
    ]
}

The chain runs bottom-up. Swapping the top link is the only difference between the modes: in dev the styles live inside the bundle and are replaced on the fly, in prod they are extracted into a file the browser caches separately from the JS.

resolve: {
    alias: {
        "@": srcFolder,
        '@img':  path.join(srcFolder, 'assets/img'),
        "@js":   path.join(srcFolder, 'assets/js/'),
        "@scss": path.join(srcFolder, 'assets/styles/')
    },
    extensions: ['.js', '.json', '.jsx', '.ts', '.tsx']
}

Aliases take ../../ out of the imports and make moving a file safe. extensions lets you write import x from './modules/design' with no extension — and it also explains why the rules cover .ts and .jsx: the starter assumes TypeScript or React will be added to the project.

optimization: {
    splitChunks: { chunks: 'all' },
    minimize: isProd,
    minimizer: isProd ? [ new CssMinimizerPlugin(), new TerserPlugin() ] : []
}

In the demo build this rule produces the second file, 202.[hash].js — that is where @babel/polyfill from the entry point went. The point is caching: application code changes often, dependencies rarely, and splitting them keeps the browser from re-downloading the second along with the first.

Known defects

An honest list. The first four are what had to be fixed: out of the box the build died before the config had even been read. The rest is still in the code.

  • fixedAn ajv version conflict killed the config at require time Cannot find module 'ajv/dist/compile/codegen'. The outdated optimize-css-assets-webpack-plugin pulls ajv@6 into the root node_modules, while ajv-keywords@5 (via schema-utils → mini-css-extract-plugin) needs ajv@8. The plugin was replaced with css-minimizer-webpack-plugin, which was already in the dependencies.
  • fixedTLS certificate read at the top level of the module fs.readFileSync for the dev-server certificate ran while the config was being loaded, so a missing src/certs/webpack-2023+1.pem broke the production build as well — and the repository holds only mkcert.exe, no .pem at all. Wrapped in fs.existsSync with a fallback to http.
  • fixedWrong path to the page template HtmlWebpackPlugin had ./pages/index.html written into it, while the only html file sits at src/templates/pages/index.html.
  • fixedStyles never made it into the build at all The entry point is assets/js/script.js alone, and no module imported styles.scss. So sass-loader and MiniCssExtractPlugin were configured but dead, and the page was built without a single style. import '@scss/styles.scss' was added; that then surfaced @import "_fonts.scss" and "_preloader.scss" against files with no underscore — fixed too.
  • openisDev is not tied to mode The mode the loaders see comes from an environment variable; the configuration's mode field has no effect on them. Running webpack --config-name dev without NODE_ENV=development gives you webpack's dev mode but the prod loader chain. The only thing holding this together is cross-env in the npm scripts.
  • openTwo configurations share one object and one directory Object.assign({...}, vendorConfig) copies references, so dev and prod use the same plugin instances, the same output and the same dist with clean: true. Running both configurations in one pass means the second erases the first's result.
  • opentype: 'asset/resource' and file-loader at the same time In webpack 5, asset/resource is the built-in replacement for file-loader. Naming both in one rule is a conflict: the file gets processed twice. The defect stays invisible in the demo build only because the single image (AuthCode.png) is imported nowhere.
  • openDead code and outdated dependencies CopyWebpackPlugin = import('copy-webpack-plugin') assigns a dynamic import to a const, so the variable holds a promise; the block that uses it is commented out, and as written the plugin would not work. devDependencies still carry optimize-css-assets-webpack-plugin (the one that broke the build) and eslint-loader, superseded by eslint-webpack-plugin. @babel/polyfill has been deprecated since Babel 7.4 in favour of core-js + regenerator-runtime.
  • openLoose ends in the build output <title> is still Document. The CSP allows 'unsafe-inline' and 'unsafe-eval' in script-src, which throws away most of the point of having a policy at all. git carries src/certs/mkcert.exe — a 4.7 MB Windows binary — and 57 MB of Yu Gothic fonts that cannot reach the build under any circumstances, because fonts.scss is zero bytes.
  • openThe demo page is empty in substance The markup is six headings (Preloader, Header, Section 1, Article 1–3, Aside, Footer), and the block SCSS partials are selectors with no properties. What is worth judging here is the configuration, not the result.
